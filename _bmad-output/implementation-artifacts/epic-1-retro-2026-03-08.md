## What Went Well

1. **Well-scoped stories with clear dev notes** — Both stories had explicit "What NOT to Do" sections, existing code context, and recommended implementation approaches. This prevented scope creep effectively.

2. **Additive changes to existing infrastructure** — Story 1.1 enhanced an existing, working CI pipeline rather than rewriting it. The enhancement was minimal (checksum generation + upload) and cleanly integrated.

3. **Security hardening through review** — Cubic code reviews caught real issues: fail-fast on missing checksums, sudo guidance removal. Both stories independently improved their checksum verification from "skip on missing" to "abort on missing."

4. **Architecture simplification** — Story 1.2 originally planned a `scripts/install.sh` + root delegator pattern but consolidated to a single `install.sh`. The simpler approach was better.

5. **Sequential story ordering worked** — Story 1.2 depended on 1.1's checksum format. Building sequentially avoided integration issues.

---

## Challenges & Growth Areas

1. **POSIX shell compatibility caused significant rework** — Story 1.2 had 6 fix commits after the initial implementation, most related to POSIX compatibility:
   - TMPDIR environment variable shadowing
   - sed portability issues between Linux and macOS
   - Bashisms creeping into POSIX shell script
   - `exec` preventing EXIT trap cleanup

2. **No static analysis for shell scripts** — ShellCheck was not available locally. Several POSIX issues could have been caught pre-commit with ShellCheck.

3. **Initial security posture was too lenient** — Both stories initially handled missing checksum entries by skipping verification rather than aborting. This was caught in review but should have been the default approach from the start.

---

## Key Insights

1. **"What NOT to Do" sections in story specs are highly effective** — They prevented scope creep and kept both stories focused. This pattern should continue for all future stories.

2. **Language paradigm switching has a cost** — Moving from Rust (strong type system, compiler safety) to POSIX shell (no type system, no compiler) removed safety nets. Future shell script work should budget extra review time and use static analysis tools.

3. **Security-first defaults should be standard practice** — Operations involving checksum verification, authentication, or security should always fail-closed (abort on failure), not fail-open (skip on failure). This should be a team standard, not something caught in review.

4. **Review-driven iteration works well for shell scripts** — In the absence of Rust's compiler, the Cubic review process served as an effective quality gate. Each review cycle improved the script's robustness.
