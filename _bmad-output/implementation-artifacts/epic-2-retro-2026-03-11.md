## What Went Well

1. **Foundational framework design was clean** — Story 2.1 (zopp-sync crate) merged with zero review findings. The `SyncTarget` trait, `DiffEngine`, and error types were well-designed from the start. This foundation will be reused by Epics 3, 4, 5, and 7.

2. **Trait-based mocking strategy worked excellently** — Story 2.2 used an internal `SecretsManagerApi` trait for testing instead of HTTP-level mocking. This produced clean, readable tests (10 tests) without complex infrastructure.

3. **Comprehensive output component system** — Story 2.3 built a full output framework (8 components, 32 tests) covering color/no-color, TTY, JSON modes, and exit code contracts. This system is immediately reusable for all future sync targets.

4. **Review process caught real issues** — The Cubic + owner review pipeline caught critical problems: silent error swallowing (PR #83), overly broad error classification (PR #83), shared args for read-only commands (PR #84), missing partial-failure exit codes (PR #84). These were all genuine quality improvements.

5. **Stacked PR chain worked** — Despite the complexity of rebasing 5 dependent PRs, the stacked PR workflow successfully maintained code quality and enabled incremental review.

## Challenges & Growth Areas

1. **Error handling design was initially wrong** — Story 2.2's `fetch_current()` silently dropped per-key errors, returning only successfully fetched secrets. This violated the principle of "return partial results WITH errors for caller to decide." The fix required a new `FetchResult` type that cascaded changes through Stories 2.4 and 2.5.

2. **MSRV mismatch blocked local verification** — Local rustc (1.88) couldn't compile the AWS SDK (requires 1.91+). This meant no local `cargo check` for the full CLI, forcing reliance on CI for compilation verification. Resolved mid-epic by updating to rustc 1.94.

3. **Trait signature changes cascaded across PRs** — When `fetch_current()` changed from `Result<HashMap, SyncError>` to `Result<FetchResult, SyncError>` during PR #83 review, both PR #84 and PR #80 needed the same fix after rebase. This created redundant work.

4. **Read-only vs write-only args were shared** — `diff aws` inherited `--dry-run` and `--force` from `SyncCommonArgs`, even though diff is read-only. This was caught by Cubic and fixed by creating a separate `DiffCommonArgs`.

5. **Error classification was too broad** — The initial `"connection"` substring check in `client.rs` would match any error message containing "connection" (including API errors about connection pools). Fixed to use specific patterns: `"dispatch failure"`, `"timeout"`, `"connection refused"`, `"connection reset"`, `"connect error"`.

---

## Key Insights

1. **"Return both successes AND errors" should be a default pattern** — When fetching collections with per-item potential failures, always return a result containing both the successful items and the per-item errors. Let the caller decide policy. Never silently discard errors.

2. **Read-only commands need separate args from write commands** — The `DiffCommonArgs` vs `SyncCommonArgs` split should have been designed from the start. Story specs should explicitly call out which flags apply to which command types.

3. **Trait signature stability matters in stacked PRs** — When a trait's return type changes during review of an early PR, all downstream PRs need the same fix. Consider batch-fixing in one pass during the rebase step rather than discovering compilation failures in CI.

4. **Error classification should use specific patterns** — Broad substring matching (`"connection"`) is a trap. Use specific, known error patterns from the SDK. This is more fragile to SDK changes but far less likely to misclassify errors.

5. **Local toolchain alignment prevents wasted CI cycles** — Upgrading from rustc 1.88 to 1.94 eliminated an entire class of "can't verify locally" problems. The first CI run for PR #84 after rebase failed on compilation — a failure that would have been caught instantly with a local `cargo check`.
